BioTime Migration Guide

Migration from ISPADMIN2 to IBN-SERVER

ItemValue
Old live machineISPADMIN2
New serverIBN-SERVER
BioTime URL on new serverhttp://192.168.64.4:8081
Database namebiotime
SQL loginISPAdmin
Migration methodSchema Compare + Data Compare, because backup/restore is blocked by SQL Server version difference
Important: During final migration, do not let ISPADMIN2 and IBN-SERVER both receive live attendance punches at the same time. Stop the old BioTime system first, then sync schema/data, then start the new server.

Before Migration

  1. Confirm BioTime opens on IBN-SERVER at http://192.168.64.4:8081.
  2. Confirm these services are running on IBN-SERVER:
bio-redis    Running
bio-cache    Running
bio-monitor  Running
  1. Confirm the SQL login exists and is enabled on IBN-SERVER:
USE master;
GO

SELECT name, is_disabled
FROM sys.sql_logins
WHERE name = 'ISPAdmin';
GO

If the login is disabled:

USE master;
GO

ALTER LOGIN ISPAdmin ENABLE;
GO
  1. Keep a rollback copy of the current IBN-SERVER database if needed. If the current database is only a test database, rename it before final sync:
ALTER DATABASE biotime MODIFY NAME = biotime_before_migration;
GO

Final Migration Steps

  1. Choose a quiet time. Do the final migration when no employees/devices are actively sending attendance punches.
  2. Stop BioTime services on ISPADMIN2. Open Command Prompt as Administrator on ISPADMIN2:
net stop bio-monitor
net stop bio-cache
net stop bio-redis

If there are other BioTime or ZKTeco services, stop them also.

  1. Stop BioTime services on IBN-SERVER. Open Command Prompt as Administrator on IBN-SERVER:
net stop bio-monitor
net stop bio-cache
net stop bio-redis
  1. Run Schema Compare. In Visual Studio or SQL Compare:
SideDatabase
SourceISPADMIN2 live biotime database
TargetIBN-SERVER biotime database

Include these object types:

  • Tables
  • Views
  • Stored procedures
  • Functions
  • Triggers
  • Indexes
  • Primary keys
  • Foreign keys
  • Default constraints
  • Check constraints
  • Schemas
  • User-defined types
  • Sequences, if any

Apply the schema update to IBN-SERVER.

  1. Run Data Compare.
SideDatabase
SourceISPADMIN2 live biotime database
TargetIBN-SERVER biotime database

Copy/sync all BioTime tables, not only attendance tables. Include:

  • Employees/personnel
  • Attendance transactions
  • Devices
  • Schedules/shifts
  • Holidays/leaves
  • Departments/areas
  • User accounts
  • System settings/configuration
  • Calculation/result tables
  1. Fix SQL user mapping on IBN-SERVER.
USE biotime;
GO

ALTER USER ISPAdmin WITH LOGIN = ISPAdmin;
GO

ALTER ROLE db_owner ADD MEMBER ISPAdmin;
GO
  1. Update statistics on IBN-SERVER.
USE biotime;
GO

EXEC sp_updatestats;
GO
  1. Optional but recommended: check database integrity.
USE master;
GO

DBCC CHECKDB ('biotime') WITH NO_INFOMSGS;
GO

No output means no detected errors.

  1. Clear Redis cache/queue on IBN-SERVER. This prevents old queue data from affecting the newly migrated database.
cd /d C:\ZKBioTime\redis

ren appendonlydir appendonlydir_bak_migration
mkdir appendonlydir

If these files exist, rename them also:

ren appendonly.aof appendonly.aof.bak_migration
ren dump.rdb dump.rdb.bak_migration
  1. Start BioTime services on IBN-SERVER.
net start bio-redis
net start bio-cache
net start bio-monitor

Confirm in Services:

bio-redis    Running
bio-cache    Running
bio-monitor  Running
  1. Test BioTime on IBN-SERVER. Open http://192.168.64.4:8081 and test:
  • Login
  • Employees open correctly
  • Devices open correctly
  • Attendance records exist
  • Manual correction works
  • Attendance recalculation works
  • Reports generate correctly
  1. Redirect devices/users to IBN-SERVER.
Server IP: 192.168.64.4
BioTime URL: http://192.168.64.4:8081
  1. Keep ISPADMIN2 stopped as rollback. Keep the old PC unchanged for a few days, but do not allow it to receive new live attendance punches.

Final Rule

Stop old BioTime
Sync schema
Sync data
Fix SQL user mapping
Clear Redis queue on new server
Start new BioTime
Test
Redirect devices/users
If there is any problem after migration, point users/devices back to ISPADMIN2 only if IBN-SERVER has been stopped first. Avoid running both systems as live systems at the same time.
